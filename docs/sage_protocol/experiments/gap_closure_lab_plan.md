# SAGE Gap-Closure Lab Plan

## Status
Experimental setup only. This branch is not final claim hardening and this document is not protected final evidence.

## Branch Objective
Use `exp/sage-gap-closure-lab` for isolated experiments that try to close the remaining SAGE capability gap beyond protected best3 and validated V2.6 evidence. The branch may change code and experimental registries, but those changes are exploratory until separately validated and reviewed.

The global working agreement in `docs/sage_protocol/00_global_working_agreement.md` has been read and remains controlling: SAGE evidence must come from the SAGE pipeline with provenance, matched comparisons must use the same scenario order and model, and helpers must preserve side-effect tools.

## Protected Assets
Do not modify:

- `artifacts/registry_frozen_best3_claim/registry_manifest.json`
- locked best3 evidence
- locked formal evidence
- final-package claim artifacts
- existing final claim summaries, except for explicitly experimental cross-references if human-approved later

Experimental outputs must stay under:

- `artifacts/registry_experiments/gap_closure_lab/`
- `artifacts/experiment_manifests/gap_closure_lab/`
- `docs/sage_protocol/experiments/`

## Split Protocol
The machine-readable split manifest is generated by:

```bash
PYTHONPATH=src:. python scripts/make_gap_closure_lab_manifest.py
```

Default output:

- `artifacts/experiment_manifests/gap_closure_lab/gap_closure_lab_splits.json`
- `artifacts/experiment_manifests/gap_closure_lab/gap_closure_lab_splits.json.sha256`

Split policy:

| Split | Size | Label access | Use | Evidence status |
| --- | ---: | --- | --- | --- |
| `seed_dev_labeled` | 8 | allowed | pain-point analysis, tool design, generation prompt repair, validation examples | never final evidence |
| `pilot_unseen` | 20 | not allowed before sealed run | Micro20 natural and force diagnostics | diagnostic only |
| `confirm_unseen` | 100 | not allowed before sealed run | matched confirmation, ablations, adoption measurement | confirmation evidence only |
| `scale_unseen` | 250 | not allowed before sealed run | scale validation after confirm-positive result | experimental scale evidence |

Seed/dev base task families are excluded from all unseen splits. Scenario IDs are recorded for auditability only and may not be hard-coded into generated tools, routers, prompts, repairs, or expected outputs.

## Leakage Controls
- No hidden truth labels outside `seed_dev_labeled`.
- No scenario selection based on baseline cache availability.
- No prior SAGE traces reused as candidate-arm outcome evidence.
- No code or registry changes between matched comparison arms.
- No tool may encode scenario IDs, expected answers, hidden facts, task-specific strings, or final labels.
- Force-call diagnostics can establish latent value or failure mode, but cannot promote a tool by themselves.
- Generated-but-uncalled tools remain unresolved until route visibility, actor adoption, schema, and value are diagnosed.

## Cache Policy
Baseline/control arms may use the control baseline cache only when the run records cache eligibility, fresh/cached counts, manifest path, cache manifest, and cache hash.

SAGE/candidate/experimental arms must be fresh runs. If any OpenAI response-cache layer is active, the run report must record configuration and prove cache keys are arm/tool/registry specific. Prefer disabling response reuse for experimental SAGE arms.

## Initial Experiment Families
Required families:

1. Many small deterministic tools.
2. Tool chaining and chain-level validation.
3. Regular tool refinement loop for underperformance, no-call, and bad-call cases.
4. Robust generation, validation, and repair loop.
5. Diverse-task pain-point synthesis into stronger reusable tools.
6. Larger model for generation and smaller model for execution.

Additional families planned for first campaign:

- Actor-policy and affordance experiments.
- Tool-router/composer experiments.
- Safe insufficient-information detector.
- Final-answer-ready transformation tools.
- Contrastive generation from positive and negative packets.
- Leave-family-out validation.
- Tool portfolio ablation and interaction testing.
- Adaptive repair from failed calls.
- Synthetic validation lab.
- Bandit-style experimental routing.
- Tool-description compression versus richness.
- Oracle-free pain point classifier.

## Fair-Chance Diagnostics
Every generated tool must be classified before it is kept, refined, or parked:

- hidden by routing
- visible but not called
- called with bad arguments
- schema/interface mismatch
- output not useful
- output not final-answer-ready
- unsafe side-effect risk
- overlap/interference with best3
- true negative value

If a tool is not called, run a small force-exposure or force-call diagnostic where safe, then repair adoption/routing/schema only on seed/dev or diagnostic samples. Do not promote from force-call alone.

## Progressive Evaluation
Use the following gate sequence:

1. Seed/dev analysis: 8 labeled tasks.
2. Micro diagnostic: 20 unseen tasks.
3. Additive pilot: 40-60 unseen tasks selected from the same manifest family pool.
4. Confirmation: 100 unseen tasks, no code changes between matched arms.
5. Scale: 250 unseen tasks only after confirmation-positive evidence.
6. Optional 500 only after a positive 250 and a clear claim objective.

Promotion to a larger sample requires outcome at least matching best3 on the prior sample, positive called-subset outcome, zero runtime exceptions, zero helper side-effect incidents, acceptable VNC/context-pollution profile, and no leakage finding.
